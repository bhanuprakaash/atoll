# MCP servers: test contract

Extends [skills-contract.md](skills-contract.md) (Bot JSON, platform tools, runs),
[chief-bot-contract.md](chief-bot-contract.md) (`create_bot`/`edit_bot`, `failsListing`) and
[README.md](README.md) (OS secret store, approvals). Tests: `mcp_servers_test.go` (Go, with
fixtures in `mcp_fixtures_test.go`) and `ui/mcp-servers.spec.ts` (Playwright). Tests build the real
server; no product package is imported. No network is used: the remote server is an `httptest`
server, the local one is a fake executable, and Context7 is only listed and picked, never run. Go
tests run through `e2e/with-secret-store`, as the GitLab tests do.

## Library

An MCP server is JSON `{id, name, kind, command, args, url, env_names, header_names}`. `kind` is
`catalog`, `local` or `remote`. A field a kind does not use is `""` or `[]`, or absent. Secret values
are never in it: `env_names` and `header_names` are names only. The same JSON is the item of every
list and reply below and of `list_mcp_servers`.

- The catalog has one entry now: `{id: "context7", name: "Context7", kind: "catalog", url:
  "https://mcp.context7.com/mcp"}`. It is remote with no sign-in and no secret. It is always the
  first item and cannot be edited or removed.
- The user's own servers follow, in the order added. Their ids are generated by Atoll (never
  `context7`).

| Request | Body | Reply |
| --- | --- | --- |
| `GET /api/mcp-servers` | | `200` array: the catalog entry, then the user's servers |
| `POST /api/mcp-servers` | local: `{name, command, args?: [string], env?: {NAME: value}}`; remote: `{name, url, headers?: {Name: value}}` | `201` the server |
| `PUT /api/mcp-servers/{id}` | the same body as `POST`, whole | `200` the server |
| `DELETE /api/mcp-servers/{id}` | none | `204` |

- `POST` is local when it has `command`, remote when it has `url`. `400` with `error` text when: there
  is no `name`; `name` is not `[A-Za-z0-9_-]+` or is `atoll` (the name is the key in the provider's
  config, so tool names read `mcp__<name>__<tool>`); both or neither of `command` and `url`; `url` is
  not `http` or `https`; `env` or `args` on a remote, `headers` on a local. `409` when another user
  server has the name. `PUT` refuses the same way (`409` for renaming onto another's name).
- `PUT` and `DELETE` address only the user's servers: an unknown id and `context7` are `404`.
- `PUT` replaces the server. `env` (local) and `headers` (remote) left out keep every stored secret.
  When present they are the whole set: a name with a value stores that value, a name with `""` keeps
  the stored value of that name, a name left out is removed and its secret deleted. The Edit form
  shows the stored names as `NAME=` lines on this rule (see the UI).
- `DELETE` removes the server from every Bot's `mcp_servers` and deletes its secrets.

## Secrets

Env values and header values go to the OS secret store: service `atoll`, username
`mcp:<server id>:env:<NAME>` or `mcp:<server id>:header:<Name>`, the value stored as given. The
tests read them with `secret-tool lookup` (`security` on macOS), not through Atoll, and see an entry
deleted by `DELETE` gone. No secret value appears in: any API reply, SSE event or MCP tool result;
`atoll.db` or any other file under `ATOLL_DATA_DIR` (checked after the server is stopped and after
runs, so the provider's config is not left in a file there); the server's stderr. Names are not
secret and may be stored in the database.

## Bots pick servers

Bot JSON gains `mcp_servers`: an array of library ids (`context7` included), default `[]`, on `GET`
and in the body of `POST /api/bots` and `PUT /api/bots/{id}` (left out keeps; an array replaces the
whole set). An id the library does not list is `400`; `error` contains that id and the id of every
server the library lists, and nothing is created or changed. A Bot has exactly the servers it picks.

Chief: `create_bot` and `edit_bot` declare `mcp_servers` (array of string) in their `tools/list`
`inputSchema`. An unknown id fails like an unknown repo (the text contains it and every known id;
no Bot created or changed, no `platform_changed`). `edit_bot` with `mcp_servers` records one `edit`
change; its Undo restores the earlier picks. A new read tool `list_mcp_servers` (no arguments, same
visibility as `list_bots`: only for a Bot with the platform switch) answers the text JSON array that
`GET /api/mcp-servers` returns.

## What a run gets

A run's provider gets Atoll's own server plus exactly the servers its Bot picks, from the library at
the time the run starts (a resumed thread too):

| Provider | Config | Local server | Remote server |
| --- | --- | --- | --- |
| Claude | `--mcp-config` `mcpServers.<name>` | `{type: "stdio", command, args, env}` (`type` may be left out) | `{type: "http", url, headers}` |
| Codex | `config.mcp_servers.<name>` of `thread/start` and `thread/resume` | `{command, args, env}` | `{url, http_headers}` |

`<name>` is the server's name. `env` and `headers` hold the real values from the secret store. The
Claude allow list stays `mcp__atoll` only, so a call to any other server goes through the
permission prompt tool; Codex's `mcpServer/elicitation/request` for a server other than `atoll` is
no longer declined but becomes an approval (answered `{action: "accept"}` or `{action: "decline"}`).

- **Approval**: a tool call to a user-added server opens an approval in the thread, as any other
  tool does (`approval` event, run `waiting` until answered, `POST /api/approvals/{id}`). The
  event's `tool` plus its `input`, as text, contain the server's name and the tool's name (Claude:
  `tool` is `mcp__<server>__<tool>`; Codex: the elicitation's `serverName`, `message` and `_meta`).
  Atoll's own tools (`finish_run`, `approve`, the platform tools) still need none: the tests count
  the approvals of a run and expect exactly one per call to a user-added server. Denied, the call
  never reaches the server.
- **Edit and Remove apply from the next run**: a live run keeps the config it started with while
  the library changes; the next run, in the same thread, has the edited server and lacks the
  removed one.
- A Bot that picks nothing gets neither server: the fake local server is not started, the remote one
  sees no request.

## UI

Settings gets a nav link `MCP servers` (`/settings/mcp-servers`). The page has:

- a `list` named `Catalog` with one `listitem` per catalog entry, containing the name and URL
  (`Context7`, `https://mcp.context7.com/mcp`);
- a `list` named `Your servers` with one `listitem` per user server (no item when there is none),
  containing the name, what it runs (a local server's command and arguments, a remote server's
  URL), and its env or header names. Never a value. Each item has buttons `Edit` and `Remove`;
- buttons `Add local` and `Add by URL`.

`Add local` opens a `dialog` named `Add local` with textboxes `Name`, `Command`, `Args` (one argument
per line) and `Env` (one `NAME=value` per line) and a button `Add`. `Add by URL` opens a `dialog`
named `Add by URL` with `Name`, `URL` and `Headers` (one `Name: value` per line) and `Add`. `Add`
sends `POST /api/mcp-servers`, closes the dialog and shows the new item. `Edit` opens a `dialog`
named `Edit <name>` with the same textboxes filled: `Env` or `Headers` hold the stored names as
`NAME=` / `Name: ` lines with no value (`FAKE_MCP_TOKEN=`), and a button `Save` sends `PUT`.
`Remove` sends `DELETE` at once and the item goes.

Bot settings (the `Bot settings` dialog) gets a `group` named `MCP servers` with one `switch` per
library server (catalog included), its accessible name the server's name. Flipping one saves at
once, as the other settings do, as `PUT /api/bots/{id}` with `mcp_servers`.

A thread's approval for a user-added server says `Wants to use ` followed by text containing the
server's name, with the `Allow` and `Deny` buttons of any other approval.

## Fakes

- `e2e/fakes/mcpstdio` (built by `TestMain` and by `ui/atoll.ts`): a local MCP server on stdio. Tool
  `answer` answers `stdio-answer-42`; tool `inspect` `{env: <name>}` answers
  `args=<its arguments joined by |>;env=<first 12 hex digits of the SHA-256 of that variable, or
  (unset)>`: the answer proves the value arrived without holding it, since a run stores its answers.
  Each start is logged to `<executable>.log` (arguments only, never env) so a test counts starts.
- The remote fake is an `httptest` server in the tests: `POST` only, every request must carry header
  `X-Fake-Key: fake-mcp-key-1` or it is `401`; tool `answer` answers `http-answer-42`.
- Both fake providers read stdio servers too (Claude `command`/`args`/`env`, Codex
  `mcp_servers.<name>.command`/`args`/`env.*`) next to HTTP ones (`url`, `headers` / `http_headers`).
- Scenario `mcp-use` (both fakes, recordings `mcp-use`): the prompt `Use MCP tools. ` followed by a
  JSON array of `{server, tool, args}`. For each call on a server the config holds, the fake prints
  the tool call, asks (Claude: the `--permission-prompt-tool`; Codex: an elicitation request, ids
  `9001`..., only for a server whose `mcp_servers.<name>.default_tools_approval_mode` is `prompt`;
  otherwise it calls unasked, as real Codex does for read-only tools), and on allow calls the
  server and prints its answer; on deny it prints `denied`.
  A server the config lacks is not called. The reply is one line per call:
  `<server>/<tool>: <answer>` (`denied`, or `unavailable` for a missing server).
- `TestMCPFixtures_ProviderScenarios/{claude,codex}/{allow,deny}` drives the fakes by hand against
  stub servers, so the fakes are proven before the product writes any MCP config. The Codex
  elicitation shape (`serverName`, `message`, `_meta.codex_approval_kind: "mcp_tool_call"`,
  `_meta.tool_params`) matches real codex-cli 0.165.0. Real Codex names the tool only in `message`
  and in the `mcpToolCall` item it starts just before; `_meta.tool_title` is the tool's optional
  MCP `title` (Context7: "Resolve Context7 Library ID"), so the fake leaves it out.

## From connections (after #62)

Tests: Go `mcp_github_test.go` (with the fake GitHub of `github_fixtures_test.go`, env
`ATOLL_GITHUB_URL` and `ATOLL_GITHUB_MCP_URL` as in [github-connection-contract.md](github-connection-contract.md))
and `ui/mcp-github.spec.ts`. "GitHub's MCP URL" below is `ATOLL_GITHUB_MCP_URL`, default
`https://api.githubcopilot.com/mcp/`.

A GitHub connection **exists** when `GET /api/connections` lists one of kind `github` with status
`connected` or `needs_sign_in`. A `pending` one (device flow started, not finished) does not count.

**The row.** While one exists, `GET /api/mcp-servers` and `list_mcp_servers` list one more item,
after the catalog and before the user's servers:

```json
{"id": "github", "name": "GitHub", "kind": "connection", "url": "<GitHub's MCP URL>"}
```

Fields a kind does not use are `""`/`[]` or absent, and `status` is absent, as for a user server. The
row is not a library server the user owns:

- `PUT /api/mcp-servers/github` and `DELETE /api/mcp-servers/github` are `400` with `error` text
  while the connection exists, and nothing changes; with no connection `github` is an unknown id
  (`404`, as for any). The user's own servers never have the id `github` (ids are generated).
- A Bot cannot pick it: `mcp_servers: ["github"]` is `400` (the error names `github`). A Bot gets the
  server through its `connections` (see below). Bot settings shows no `switch` named `GitHub` under
  `MCP servers`.
- It follows the connection: no row before the sign-in finishes, the row once `connected`, and the
  row stays while the connection `needs_sign_in`.

**Settings UI.** While the connection exists, the page has a `list` named `From connections`, after
`Catalog` and before `Your servers`, with one `listitem` containing `GitHub`, the URL and the text
`from GitHub connection` (its own element), and no button in it. With no connection there is no
`From connections` list and no such text. The catalog and `Your servers` lists are unchanged (the
row is in neither).

**"GitHub has a connection".** The API does not dedupe: `POST /api/mcp-servers` with a remote at
GitHub's MCP URL is `201` as any other. The check is in the `Add by URL` dialog: when `Add` is
pressed and the typed URL equals GitHub's MCP URL, ignoring surrounding spaces and one trailing `/`,
while the connection exists, the page sends no request and the dialog stays open showing the text
`GitHub has a connection` with buttons `Use connection` and `Add anyway`.

- `Use connection` closes the dialog and adds nothing: no `POST /api/mcp-servers`, no new item.
- `Add anyway` sends the `POST` as typed (name, URL as typed, headers), closes the dialog and shows the
  new item in `Your servers`.
- With no connection, or any other URL, `Add` sends the `POST` at once and shows no such text.

**A Bot with both.** A Bot's `connections` holds the GitHub connection (`connected`) and its
`mcp_servers` picks a user server whose URL equals GitHub's MCP URL (the same comparison as the
dialog's; the tests use the identical string). Its run's provider config then holds exactly one
entry for that URL: the connection's `github` (the Bearer token of the connection, as
[github-connection-contract.md](github-connection-contract.md) says). The user's server is left out
of the config altogether: no entry for its name and none of its headers sent. Proof: the fake provider's view
of its config (Claude's `--mcp-config`, Codex's `thread/start` config) names `github` and `atoll`
only, and the fake GitHub MCP server sees only `Authorization: Bearer <the connection's token>`
(one `get_me` call from the `github-probe` scenario) and never the user server's header. The pick
itself is kept: `GET /api/bots/{id}` still lists it. A Bot that picks the same user server **without**
the GitHub connection gets it as the user made it (its own name, URL and headers, and no `github`
entry): the dedupe is only against the connection's entry in the same run.

When `ATOLL_SECRET_STORE_UNAVAILABLE` is non-empty, every secret-store read and write fails on
Linux and macOS. A secret save failure reports that the system keychain could not save the
credentials, with an HTTP status of 500 or greater.

## Not covered

- From connections: a user server named `github` (it would share the key of the connection's
  entry), a signed-out or deleted GitHub connection (no route for it), a Bot with both whose user
  server spells the URL with a trailing `/` difference, `list_mcp_servers` showing the row (same JSON
  as `GET`, not asserted), and the absence of a `GitHub` switch in Bot settings.
- `docs/design.md` and "the tests land first" (not software-checkable here).
- A real stdio server, a real remote server, real Claude and real Codex reading the config, and
  Context7 itself (no network). A Bot picking `context7` is tested through the API only.
- That a Bot without the platform switch lacks `list_mcp_servers` (the scenario `platform-denied`
  checks a fixed tool list that this ticket does not extend).
- The look of the page, the dialogs and the switches; only roles, names and texts are pinned.
